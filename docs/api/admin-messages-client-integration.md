# Admin Messages — Frontend Integration Guide

How the game client consumes server-driven announcements (`AdminMessage`): the two endpoints,
their exact payloads, when to call them, and how to render the HTML safely.

This is the client-side companion to [server-driven-messaging.md](server-driven-messaging.md),
which is the full spec including the backend targeting rules an operator uses when authoring a
message. Nothing here contradicts that document — if the two ever disagree, the backend spec
wins and this file is stale.

**Not the same thing as `/api/inbox`.** Inbox messages are in-game fiction (agents, sponsors,
investors) generated by game services for one club. Admin messages are out-of-game
announcements written by a human operator: release notes, incident notices, targeted campaigns.
They travel on different endpoints and have different lifecycles. Do not merge their models;
you can still surface both in the same inbox UI.

---

## 1. Endpoints

| Method | Path | Auth |
|---|---|---|
| `GET` | `/api/messages/pending` | Bearer JWT, `ROLE_CLUB` |
| `POST` | `/api/messages/{id}/ack` | Bearer JWT, `ROLE_CLUB` |

Same JWT as every other game endpoint. Guest (device-bound) and registered accounts are treated
identically — nothing in this feature branches on verification status.

## 2. Types

```ts
/** Wire-level enums. Values are exactly what the API sends. */
export type MessageDisplayType = 'modal_blocking' | 'inbox_item' | 'bottom_sheet';

/** Int-backed, sorted descending by the server. 3 is the most urgent. */
export type MessagePriority = 1 | 2 | 3; // 1 low, 2 standard, 3 urgent

export interface AdminMessage {
  /** RFC 4122 UUID. Pass back verbatim to the ack endpoint. */
  id: string;
  /** Plain text, ≤ 150 characters. */
  title: string;
  /** Sanitised HTML — see §5. Can legitimately be an empty string. */
  bodyHtml: string;
  priority: MessagePriority;
  displayType: MessageDisplayType;
  /** ISO 8601 with offset, e.g. "2026-08-21T23:00:00+00:00". Publication time. */
  createdAt: string;
}

export interface PendingMessagesResponse {
  messages: AdminMessage[];
}

/** Only these two are accepted from a client. "pending" is internal and is rejected with 422. */
export type MessageAckStatus = 'displayed' | 'dismissed';

export interface MessageAckRequest {
  status: MessageAckStatus;
}
```

All keys are **camelCase**, matching the rest of this API. (Some early drafts of the spec showed
snake_case; that is not what ships.)

## 3. `GET /api/messages/pending`

No query parameters. The caller's club is derived from the JWT.

```http
GET /api/messages/pending
Authorization: Bearer <jwt>
```

```json
{
  "messages": [
    {
      "id": "01914eb1-9bc0-7111-9e23-28bf2281a8b1",
      "title": "Season 2 Update: New Youth Facilities",
      "bodyHtml": "<p>Academy upgrades now provide <strong>+15% XP</strong>.</p>",
      "priority": 2,
      "displayType": "modal_blocking",
      "createdAt": "2026-08-21T23:00:00+00:00"
    }
  ]
}
```

### Guarantees

- **`messages: []` is the normal case**, not an error state. Most polls return nothing.
- **Capped at 6 per response**: at most **one** `modal_blocking` message plus at most **five**
  non-blocking ones. The cap is enforced server-side, so a misconfigured campaign cannot stack
  modals on a player.
- **The blocking message, if present, is always first** in the array.
- **Ordering** is `priority` descending, then oldest-first within the same priority.
- **A message keeps coming back until it is acked.** A dropped response loses nothing.
- **No ETag / no caching.** Unlike `/api/archetypes`, this response is per-caller and changes on
  every acknowledgement, so do not add conditional-request handling — a 304 would suppress a
  message the player never saw.

### Errors

| Status | Body | When |
|---|---|---|
| `401` | Symfony auth error | Missing/expired JWT — refresh and retry |
| `404` | `{"error": "Club not found"}` | Authenticated, but the account has no club yet |

`404` is expected during onboarding, before `POST /api/club/initialize` has run. Treat it as
"nothing to show", not as a failure to report.

## 4. `POST /api/messages/{id}/ack`

```http
POST /api/messages/01914eb1-9bc0-7111-9e23-28bf2281a8b1/ack
Authorization: Bearer <jwt>
Content-Type: application/json

{ "status": "displayed" }
```

Response: `200 {"success": true}`.

### Semantics

- **Ack on render, and again on dismiss.** Both calls are safe. The server performs an atomic
  upsert keyed on `(user, message)`, so repeats never duplicate a record and the two calls may
  race freely.
- **`dismissed` is terminal.** A late-arriving `displayed` ack cannot walk a dismissed message
  back to a weaker state.
- **Either status retires the message** — after a successful ack of either kind, the message
  stops appearing in `/pending`. So acking on render alone is enough to prevent a re-show; the
  dismiss ack exists to record intent, not to suppress.
- **Acks are per account, not per club.** Starting a new club does not replay announcements the
  player already dismissed, and acking does not require a club at all — a message can be retired
  after the club is deleted or replaced.
- **A guest who registers a real email becomes a new account** and may re-see a message they
  dismissed as a guest. That is a known account-linking gap in registration, not something the
  client can work around.

### Errors

| Status | When | Client action |
|---|---|---|
| `400` | Malformed JSON body | Bug — fix the request |
| `401` | Missing/expired JWT | Refresh and retry |
| `404` | Unknown, malformed, or deleted message id | Drop the message locally; do not retry |
| `422` | `status` was `"pending"`, missing, or not one of the two accepted values | Bug — fix the request |

A failed ack is safe to retry later: the message simply reappears in the next poll.

## 5. Rendering `bodyHtml`

`bodyHtml` is sanitised **when the operator saves it**, so what the API returns is already clean.
Surviving tags — and this is the complete list:

`p`, `strong`, `em`, `ul`, `ol`, `li`, `br`, `h3`, and `a` with an `href`.

- Link schemes allowed: **`https:` and `buildmyclub:`** (the app's own deep-link scheme). Handle
  `buildmyclub:` via `Linking` / your router rather than opening it in a browser; `http:`,
  `javascript:` and `mailto:` are stripped at write time.
- Every `<a>` is forced to `rel="noopener noreferrer"`.
- **`style` and `class` are stripped everywhere.** The client owns its retro theme; operator CSS
  must never bleed into it.
- Scripts, iframes, images and event-handler attributes cannot be saved in the first place.

Render through a strict allowlist of your own anyway — defence in depth, and the list above is
the exact set worth styling:

```tsx
import RenderHtml from 'react-native-render-html';

<RenderHtml
  contentWidth={width}
  source={{ html: message.bodyHtml }}
  tagsStyles={{ p: {...}, strong: {...}, em: {...}, ul: {...}, ol: {...}, li: {...}, h3: {...}, a: {...} }}
  ignoredDomTags={['script', 'iframe', 'img', 'style']}
  allowedStyles={[]}
/>
```

**Handle an empty `bodyHtml`.** Nothing on the backend requires a non-empty body, and content
that sanitises down to nothing (e.g. an operator pasting a styled block from a doc) is stored as
`""`. Render the title alone rather than an empty card.

## 6. Display routing

| `displayType` | Presentation |
|---|---|
| `modal_blocking` | Full modal that interrupts play. **One per session**, even though the server already caps it at one per response. |
| `inbox_item` | Route to the club Inbox under a `system` category. Do not interrupt. |
| `bottom_sheet` | Non-blocking sheet, or the inbox if a sheet is inconvenient. Do not interrupt. |

`priority` drives ordering and visual weight (badge colour, sort position in the inbox), not
whether the message interrupts — that is `displayType`'s job alone.

---

## 7. Polling policy

**Do not poll on the local week tick.** The sim advances weeks rapidly while offline and would
cause connection storms.

Poll on exactly two triggers:

1. **App cold start**, after SQLite hydration completes.
2. **Foreground resume** via the `AppState` listener, **debounced to at most once every 15
   minutes**.

A failed poll is not an error state — carry on and pick messages up on the next successful call.

## 8. Reference flow

```ts
const POLL_DEBOUNCE_MS = 15 * 60 * 1000;
let lastPolledAt = 0;

export async function pollAdminMessages(force = false): Promise<AdminMessage[]> {
  if (!force && Date.now() - lastPolledAt < POLL_DEBOUNCE_MS) return [];

  try {
    const res = await api.get<PendingMessagesResponse>('/api/messages/pending');
    lastPolledAt = Date.now();
    return res.messages ?? [];
  } catch (err) {
    // 404 = no club yet (onboarding). Anything else = offline/transient.
    // Both are non-events: the server keeps the message until it is acked.
    return [];
  }
}

export async function ackAdminMessage(id: string, status: MessageAckStatus): Promise<void> {
  try {
    await api.post(`/api/messages/${id}/ack`, { status });
  } catch (err) {
    // 404 => message was deleted server-side; drop it locally.
    // Anything else => leave it; it reappears on the next poll and we ack again.
  }
}
```

Wiring:

```
cold start / resume
  └─ pollAdminMessages()
       ├─ messages[0].displayType === 'modal_blocking' && no modal shown this session
       │    └─ show modal → ackAdminMessage(id, 'displayed')   [on mount]
       │                  → ackAdminMessage(id, 'dismissed')   [on close]
       └─ remaining messages → inbox (system category)
            └─ ackAdminMessage(id, 'displayed') when the row is first rendered
```

## 9. QA checklist

- [ ] Empty `messages` array renders nothing and logs nothing alarming.
- [ ] `404 Club not found` before club initialisation is silent.
- [ ] Blocking modal appears once, then never again after an ack — including after a full app
      restart.
- [ ] Acking twice (render + dismiss) produces no duplicate UI and no error.
- [ ] Airplane mode: poll fails silently; the message arrives on the next successful poll.
- [ ] Message with an empty `bodyHtml` renders the title only.
- [ ] `<a href="https://…">` opens externally; `<a href="buildmyclub://…">` deep-links in-app.
- [ ] A body containing `style="color:red"` (server-stripped) renders in the app's own theme.
- [ ] Six messages (1 blocking + 5 others) route correctly: one modal, five inbox rows.
- [ ] Starting a second club does not replay already-dismissed announcements.
